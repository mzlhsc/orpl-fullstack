# order-platform 接口文档

> 更新时间：2026-11-24  
> 服务名：`order-platform`（单体 Spring Boot）  
> 默认地址：`http://127.0.0.1:8080`；本机联调若原微服务网关占用 8080，可用 `--server.port=8095`。  
> 在线文档：`/doc.html`、`/v3/api-docs`、`/swagger-ui/index.html`。

## 1. 认证方式

| 身份 | 请求头 | 登录接口 | 默认账号/开发 code |
|---|---|---|---|
| 管理端员工 | `zmlhsc` 或 `mzlhsc` | `POST /admin/employee/login` | `admin / 123456` |
| 小程序用户 | `authorization` | `POST /user/user/login` | `code=ordpf-mp-local-user` |

- 管理员令牌只允许访问 `/admin/**`；用户令牌只允许访问 `/user/**`、`/addressBook/**`、`/shopping-cart/**`。
- 登录、商品浏览、扫码看桌台、接口文档、`/health` 为公开白名单。
- 单体不再保留 `/inner/**` 内部 HTTP 接口；原来的 23 个内部接口已删除，跨模块统计查询改为进程内调用领域 `XxxQueryService`。

## 2. 返回结构约定

多数业务接口返回统一结构 `R<T>`：`{ "code": 200, "msg": "OK", "data": ... }`。

历史接口保留原项目风格，返回结构并不完全统一：

- `POST /admin/employee/login`：直接返回 `EmployeeLoginVO`（`id/userName/name/token`）。
- `GET /admin/category/page`、`GET /admin/dish/page`、`GET /admin/employee/page` 直接返回 `PageResult`（`total/pages/list`）。
- `GET /admin/setmeal/page`、`GET /admin/order/conditionSearch` 返回 `R<PageResult>`，分页字段在 `data.total`、`data.pages`、`data.list`。
- `GET /user/category/list`、`GET /user/dish/list` 直接返回数组，不包 `R`。
- 营业额/用户/订单报表的 `dateList`、`turnoverList` 等字段是逗号分隔字符串，不是 JSON 数组。
- 订单详情 `GET /user/order/details/{id}` 的菜品明细在 `data.orderDetailList` 中；`data.orderDishes` 是管理端订单列表使用的拼接字符串，详情接口里为 `null` 属正常。

### 订单状态与自动接单变更（2026-11-24）

订单状态枚举调整为：

| 值 | 含义 |
|---|---|
| 1 | 待付款 |
| 2 | 待接单 |
| 3 | 已接单（可直接完成，不再进入派送中） |
| 5 | 已完成 |
| 6 | 已取消 |

`4 派送中`已删除；历史 `status=4` 数据通过 `mysql/03-migrate-order-status.sql` 迁移为 `3 已接单`，原 `/admin/order/delivery/{id}` 接口同步删除。

**自动接单开关**

- `GET /admin/shop/autoAccept`：返回 `{ takeoutAutoAccept, diningAutoAccept }`。
- `PUT /admin/shop/autoAccept`：body `{ takeoutAutoAccept?, diningAutoAccept? }`，可只传一个字段，未传字段保持原值；返回最新开关状态。
- 存储：Redis `SHOP_AUTO_ACCEPT_TAKEOUT`、`SHOP_AUTO_ACCEPT_DINING`，值为 `1` 开启、`0` 关闭；未设置时默认关闭。
- 行为：外卖下单命中外卖开关、堂食加菜下单命中堂食开关时，订单创建即为 `3 已接单`；关闭时仍为 `2 待接单`。开关只影响之后的新订单。
 
**支付状态**

- `PUT /admin/order/payStatus`：body `{ id, payStatus }`，`payStatus` 只允许 `0 未支付`、`1 已支付`。
- `PUT /admin/order/complete/{id}`：仅允许 `3 已接单` 的外卖订单完成；完成后同时写入 `payStatus=1 已支付`、`deliveryTime/checkoutTime`。堂食订单仍通过整桌结账完成。
- 已完成订单不能改回未支付；已取消、已退款订单不能改支付状态。

### 堂食扫码点单与加餐合并（2026-11-24）

**小程序流程**

- 扫描桌台码、员工代开台或加入同桌成功后，小程序直接进入点单页 `/pages/menu/menu`，不再跳转堂食会话页；会话详情仍可从点单页“查看本单”进入。
- 点单页为左分类栏 + 右侧菜品列表；购物车图标打开底部“已选商品”弹层，可加减数量、清空和查看合计；底部购物车操作栏贴近 TabBar 上方显示，不再悬在菜品列表中部。
- 堂食页同时支持页面内“扫码”和微信外部扫码启动参数：`onLoad` 读取 `qrToken`、`scene`、`q`，解析出桌台 token 后走同一套开台/加入逻辑，成功即 `switchTab` 到点单页，不再进入堂食会话页。
- 堂食底部主按钮文案：当前会话无已提交订单时为“下单”，已有当前订单时为“加餐”；外卖仍为“去结算”。
- “下单/加餐”进入 `/pages/cart/cart`，页面同时展示当前订单号下的历史菜品（按第几次下单分组）和本次购物车内容。
- 堂食会话页删除“已提交订单”多订单卡片，改为当前订单的菜品按“第一次下单、第二次下单……”分组展示。

**订单合并规则**

- `POST /user/dining/session/{sessionId}/submit` 每次提交仍会校验会话状态、成员身份、扣减库存并清空共享购物车。
- 同一堂食会话只复用一笔进行中的订单：
  - 首次提交创建订单，`order_detail.dining_round = 1`。
  - 后续“加餐”不再创建新订单，只向同一 `orders` 记录追加 `order_detail`，`dining_round` 递增为 2、3……，同时累加 `orders.amount` 与会话 `dining_session.total_amount`。
  - 仅复用状态为 `1待付款/2待接单/3已接单` 的堂食订单；已取消、已完成订单不会追加。
- `OrderSubmitVO` 新增 `diningRound` 字段，表示本次提交是第几次下单；`id/orderNumber` 在加餐时返回当前同一订单。

**会话详情新增字段**

`GET /user/dining/session/{id}`、`GET /user/dining/session/mine` 返回的 `DiningSessionVO` 新增：

| 字段 | 类型 | 说明 |
|---|---|---|
| `orderRounds` | array | 当前订单按轮次分组的菜品，元素含 `round`、`orderId`、`orderNumber`、`orderTime`、`amount`、`items[]` |
| `currentOrderId` | bigint | 当前堂食订单 id |
| `currentOrderNo` | varchar | 当前堂食订单号 |

`orderRounds[].items[]` 为 `order_detail` 行，新增 `diningRound` 字段，与 `orderRounds[].round` 对应。前端据此显示“第一次下单/第二次下单”。

- 旧会话若存在多笔历史订单，`orderRounds` 按订单顺序生成展示轮次并保留每轮真实的 `orderNumber`；小程序对非 `currentOrderNo` 的轮次额外标注“原订单 Dxxx”，避免旧数据被误读为同一订单号下的轮次。

## 4. 常用调用示例

以下示例以本机联调端口 `8095` 为例，正式默认端口为 `8080`，按实际启动端口替换。

### 4.1 管理端登录

```bash
curl -X POST "http://127.0.0.1:8095/admin/employee/login" \
  -H "Content-Type: application/json" \
  -d "{\"username\":\"admin\",\"password\":\"123456\"}"
```

返回裸 `EmployeeLoginVO`：

```json
{"id":1,"userName":"admin","name":"管理员","token":"..."}
```

后续请求把 token 放入 `zmlhsc` 或 `mzlhsc` 请求头。

### 4.2 管理端分页查询

```bash
curl "http://127.0.0.1:8095/admin/category/page?page=1&pageSize=10" \
  -H "zmlhsc: <token>"
```

分页接口直接返回 `PageResult`：

```json
{"total":6,"pages":1,"list":[...]}
```

### 4.3 小程序用户登录

```bash
curl -X POST "http://127.0.0.1:8095/user/user/login" \
  -H "Content-Type: application/json" \
  -d "{\"code\":\"ordpf-mp-local-user\"}"
```

返回 `R<UserLoginVO>`，用户 token 放在 `authorization` 请求头。开发环境不配置微信 appid/secret 时，code 直接当作 openid 使用。

### 4.4 用户下单

```bash
curl -X POST "http://127.0.0.1:8095/user/order/submit" \
  -H "Content-Type: application/json" \
  -H "authorization: <user-token>" \
  -d "{\"addressBookId\":21,\"payMethod\":1,\"remark\":\"测试订单\",\"deliveryStatus\":1,\"tablewareNumber\":1,\"tablewareStatus\":1,\"packAmount\":0,\"amount\":6}"
```

### 4.5 堂食开台、加菜、下单

```bash
# 开台
curl -X POST "http://127.0.0.1:8095/user/dining/open" \
  -H "Content-Type: application/json" \
  -H "authorization: <user-token>" \
  -d "{\"tableId\":1,\"guestCount\":2,\"nickname\":\"联调用户\"}"

# 共享购物车加菜
curl -X POST "http://127.0.0.1:8095/user/dining/cart" \
  -H "Content-Type: application/json" \
  -H "authorization: <user-token>" \
  -d "{\"sessionId\":42,\"dishId\":1,\"number\":1}"

# 生成堂食订单
curl -X POST "http://127.0.0.1:8095/user/dining/session/42/submit" \
  -H "authorization: <user-token>"
```

### 4.6 管理端整单结账

```bash
curl -X POST "http://127.0.0.1:8095/admin/dining/session/checkout" \
  -H "Content-Type: application/json" \
  -H "zmlhsc: <admin-token>" \
  -d "{\"sessionId\":42,\"payMethod\":1,\"settleUnpaid\":true,\"remark\":\"联调结账\"}"
```

该接口返回 `R<Void>`，业务结果看 `code=200`；结账后：

- 会话状态改为 `3已结账`，写 `checkoutTime`；
- 该会话所有未结束订单改为 `5已完成 + 1已支付`，已取消订单保持取消；
- 关联桌台状态改为 `0空闲`；
- 共享购物车清空；
- 会话成员记录保留用于支付历史，但会话不再活跃，`GET /user/dining/session/mine` 不再返回；
- 小程序会话页轮询到 `status=3/4` 后自动提示并退出会话。

### 4.6.1 管理端关闭会话

```bash
curl -X POST "http://127.0.0.1:8080/admin/dining/session/58/close?reason=现场关闭" \
  -H "zmlhsc: <admin-token>"
```

`/session/{id}/cancel` 保留为兼容旧调用，等同 `/close`。关闭后：

- 会话状态改为 `4已关闭`（底层继续复用原 `4已取消` 状态值）；
- 仅将状态为 `1待付款/2待接单/3已接单` 的订单改为 `6已取消` 并回补库存；`5已完成`、`6已取消` 和 `payStatus=1已支付` 的订单保留；
- 关联桌台状态改为 `0空闲`，共享购物车清空；
- 会话成员记录保留用于支付/AA 历史，但 `GET /user/dining/session/mine` 不再返回该会话；
- 小程序会话页轮询到 `status=4` 后提示会话已结束并退出。

关闭会话不是结账，不写支付记录；如顾客已经付款，请使用整单结账完成。

管理端桌台卡片、就餐会话列表和会话详情均提供“关闭会话”入口，确认原因后执行上述接口。
